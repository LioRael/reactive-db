# 短路径与 join 汇合波动核查

基线：`e8ee6bf50e94a8fcc6cf8da45b67882bb6e93668`。本轮只操作 reactive-db 和审计工作目录；未改动 livequery、tanstack-db-rs。运行时仍为纯 Rust，无新增依赖、JS 兼容、FFI 或 unsafe。

## 结论与保留范围

**本轮不保留新增运行时优化。** 批次索引内联候选确实减少一次单集合写入分配；正反向同进程对照中，短路径按场景/堆条件汇总改善约 8.0%–15.1%。但 fanout 保护出现了跨进程、独立程序均可复现的回退。这个回退不能因某个反向程序接近零，就被归类为纯噪声。减少一次分配也会改变后续堆布局；join 算法未修改，并不保证整个程序的 join 耗时不受影响。当前没有采样/硬件计数器证据确定这个候选回退的微观原因。它不满足本轮“保留宽图与大 fanout 收益”的接收条件，已撤销。

最终 `src/`、Cargo.toml、Cargo.lock 与基线完全相同。此前宽图、fanout、稀疏调度和单行 delta 优化均保留。新增内容仅为 benchmark harness、回归测试和审计报告；因此最终版本没有本轮声称的新运行时加速，也没有引入候选的运行时退化。表中 paired/reversed/独立程序均是**被否决候选**的数据，不能当作最终版本收益。

对原来的波动，证据支持更谨慎的判断：

- 同源码控制的短路径在进程分组已出现约 −8.3% 到 +8.9%，汇合 fresh 从 −6.6% 到 +2.4%。原来方向不一致的几个百分点不能凭单个 benchmark 认定真实退化。
- 候选的 join 汇合在正向总体略快、反向慢约 2.7%–4.3%，也没有跨布局稳定收益；宽图正向 +0.5%、反向 +5.6%。本轮没有足够证据声称已消除汇合回退。
- fanout 正向三个进程均慢（+6.4%–7.5%），同名独立程序三轮也慢 8.2%、6.9%、9.4%。这是需要拒绝候选的实际风险，不能套用全局“噪声容限”予以豁免。
- 不能精确分解 allocator、实例随机哈希、代码布局、系统调度各占多少。下一次 runtime 候选仍应同时通过同源码控制、角色互换、同名独立程序和这些保护场景，而不是继续尝试只对一个编译产物有效的 inline 调整。

## 实验问题与候选

短路径每次写入仍为 `WriteBatch::patches` 分配一个 `BTreeMap` 节点，即使只触及一个集合。实验候选将最小 source ID 的补丁内联到批次，其他来源保留在有序树中，消费时保持原 source ID 顺序。这能少一次集合索引树分配/释放，不改变行补丁树、source delta、调度器、join 实现，也不复用跨写入容量。

候选补丁单独归档为 `reactive-db-fluctuation-candidate.patch`，是否保留见结论。不能将它的短路径收益直接解释成 join 优化：10,000 个汇合 join 每次仍须执行自身的增量维护，一次源索引分配只占极小部分。

## 如何区分信号

1. **同源码双 crate 对照**：基线源码复制两份，只改其中一个 package 名以让 Cargo 同时链接。算法完全相同，但编译身份、单态化代码地址以及图实例不同。这个对照可以显示“无源码优化也有差值”，并不能单独将差值归因到某一硬件原因。
2. **候选正向/反向**：独立构建两个程序，交换 old_db/new_db 的依赖身份；报告统一还原成 candidate / baseline − 1。交换角色也会改变程序代码布局，不能只挑有利的程序。
3. **图实例与堆历史**：每个场景、每种堆条件重建 4 对图，3 个独立进程。fresh 不加额外干扰（不代表重置 allocator）；churn 创建并释放 4096 个 32–1024 字节缓冲；held 保留相同缓冲到计时结束。短路径与汇合使用三种条件，宽图和 fanout 保护用 fresh。此操作改变分配历史，没有替换系统分配器。
4. **交叉顺序**：创建先后、校准先后和测量先后分别交叉。每对实例校准到约 50ms，两轮预热后四轮交替测量，两边用相同迭代数。先对四轮比值取中位数，再对 12 个实例取中位数；同时报告进程、创建、计时分组。每轮窗口不当成独立样本，只有 3 个进程，未据此作严格总体显著性断言。
5. **独立可执行文件**：Criterion 40 samples、1s warmup、3s measurement，3 轮 AB/BA/AB，并反转第二轮场景顺序。先保留双 crate 所需的 baseline 改名进行一组，然后使用原始 package 名完全相同的 baseline/candidate 进行核对。各程序单独构建，不同轮次启动新进程。每个 Criterion 测量通常复用一个图，不能用其内部置信区间代替跨实例不确定性。

所有正式测量串行执行；未同时跑测试、构建或采样 profiler。Rust 1.99.0、aarch64 macOS、系统 allocator、原 Cargo release/bench 优化设置，两个版本均用 invocation-local wrapper bypass。因本地 strip 工具兼容问题，两边都关闭 bench/release strip，不修改项目配置。

代码中 `Scheduler::entries` 和 `Stages::rest` 使用标准 `HashMap`，实例的随机哈希状态也是潜在混杂因素。这里未固定其种子、未控制 CPU 频率/调度、未测硬件计数器。因此可以判断某些小差异不稳定，但不能证明它们全由 allocator 或代码布局导致，更不能把保护场景出现的退化一概称为噪声。

## 新增语义回归

`tests/source_order.rs` 增加两个公开 API 测试：

- 三集合的全部六种写入顺序，反向重复写入，第三集合插入后取消；两条不同深度路径汇合 join，以独立全重算模型验证 12 次 key 变化，验证每个顺序的工作预算统计相同、每个事务只发布一个 epoch/delta。
- 多集合逆序与重复写入，在六个 work budget 截断点失败；使用 Weak 验证覆盖值和失败补丁全部释放，源/视图/订阅都不发布，放宽预算后原子重试成功。

既有测试继续覆盖稀疏传播、剪枝、宽图、多父汇合、自连接、预算拒绝、journal 与 lease 回收。新测试也在未优化的基线执行，确认不依赖候选私有实现。

## 复现

`benchmarks/fluctuation.rs` 是独立对照程序，不是产品 Cargo target。另建临时 Cargo 项目，将此文件复制为 `src/main.rs`，配置 `old_db` 指向改名为 `reactive-db-baseline` 的基线快照、`new_db` 指向被测快照；正反向程序只交换两个 dependency alias。不要修改正式仓库 Cargo.toml。相同代码控制则让两个依赖都指向基线源码快照。

用项目固定工具链 `cargo build --release --offline` 构建，再分别设置 `BENCH_RUN=0/1/2` 直接启动程序，将 stdout 保存为 CSV。默认本轮矩阵每个程序输出 528 行；`NULLS=1` 还可启用同版本 old_null/new_null 实例控制，本轮没有启用该额外矩阵。请使用原始 CSV 的 version 方向解释结果：reversed 文件需交换 before/after 数值以及创建/计时标签。

独立程序运行方式示例：

```sh
cargo bench --bench scheduler --offline -- 'scheduler/converging/10000$' \
  --noplot --sample-size 40 --warm-up-time 1 --measurement-time 3
```

其他场景名称和原始估计见 `reactive-db-fluctuation-separate.json` 与 `reactive-db-fluctuation-matched.json`。源修订、候选补丁摘要、测试程序二进制摘要、工具链与机器信息见 manifest。所有收益百分比负数表示耗时减少；表内 before/after 时间分别取中位数，所以它们之比不必等于配对比值的中位数。

## 最终验证

- 标准原生 Cargo：1.99.0 的 `check --all-targets --all-features`、`clippy --all-targets --all-features -- -D warnings`、debug/release `test`、`doc --no-deps`（rustdoc warnings 为错误）全部通过。
- 项目 MSRV 1.88.0 的 all-targets/all-features check 与完整 test 全部通过。每次完整测试共 **107 项**（94 单元/集成 + 13 rustdoc），无失败。
- `cargo fmt --all`、独立 benchmark rustfmt、`git diff --check` 通过；三个比较程序单独 build/clippy 通过。
- 两项新增回归在基线快照也通过；候选在撤回前通过这两项回归和 all-targets check，但未将其当作最终运行时交付。
- 内存 probe 的 10 个循环各建立 10,000 行源与派生图，owner/snapshot 释放后 `live_after_drop` 均为 0。RSS 仅作诊断，不将 allocator 未归还 OS 的页认定为泄漏。
- 运行时源码与基线逐文件 Git diff 为空；未修改依赖、工具链、全局配置或原来的两个仓库。Blaze 行为与兼容性未充分确认，本轮全部用绝对路径原生 Cargo，并在单次调用中清空 RUSTC_WRAPPER/RUSTC_WORKSPACE_WRAPPER。
