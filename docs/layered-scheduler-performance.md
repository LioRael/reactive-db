# reactive-db 万节点多层宽图：瓶颈调查与优化

日期：2026-10-26。直接基线 `8734029`；全图扫描参考 `dca6164`。
仅修改 reactive-db 和任务验证目录，未改动 livequery、tanstack-db-rs。纯安全 Rust、零运行时依赖、公共 API 不变。

## 结论

最终只采用**单后继待处理项压缩**，没有改变运行时节点表、发布流程、算子或退休逻辑。
万节点两层图（每层各 10,000 个派生节点）的长采样，两轮中位数平均耗时相较上次下降 **18.1%**，相较全图扫描原版仍高约 **3.3%**，测量区间重叠。主测试短采样中同场景约改善 8%；跨运行绝对时间波动明显，不能把不同实验的绝对时间混在一起计算收益。

这不是所有场景全面变快：主测试中万节点 join 汇合平均约慢 4.8%，无关节点/剪枝极短路径约增加 20–30 ns；这些范围完整列出。稀疏传播的复杂度优势保留，仍远低于全图扫描原版，但不能宣称完全消除所有退化。

## 定位证据与实现

用本机 `/usr/bin/sample` 对基线 release benchmark 的 `scheduler/layered/10000` 进行 5 秒、1 ms 间隔采样；Criterion 使用 `--profile-time 10`，采样与正式计时测试分开。主线程共 3,764 个栈样本，`Queue::pop_first` 出现在 409 个样本中，约 10.9%。这包含 Criterion 的执行阶段差异，且部分调用内联，**不是精确的函数独占 CPU 占比**。原始采样单独保存。

结构上，第一层的每个节点只有一个第二层后继；旧实现却为这 10,000 个待处理项保留完整 BTreeSet 迭代器，堆调整时反复搬移它们。最后一个目标不需要剩余迭代器状态。

`src/scheduler.rs` 对入队时只有一个剩余目标的序列，使用紧凑的单目标 heap，仅保存 `(rank, NodeId)`，在这台 64 位机器上是两个 64 位值。仍有多个目标的序列继续使用已有迭代器 heap，最小序列继续内联。出队时比较紧凑 heap 头与当前序列头，选择最小 rank；跨两类存储的重复 rank 仍只执行一次。堆操作的渐近复杂度未改变，优化的是数据搬移与缓存成本。

所有传播边仍在入队前按原规则收费，所有到达节点仍在求值前收费；没有绕过预算或恢复全图扫描。队列仍为单次 write 的局部状态，错误/返回后释放，无持久 visited 数组或缓冲高水位。prepare→commit 原子发布、empty delta 截断、维护状态提交、租约回收和 poison 契约保持不变。

## 回归与验证

新增 2 项回归，总计 **90 项**通过（77 unit/integration，13 rustdoc，其中 10 compile-fail）：

- 单目标、多目标、内联项互相切换并包含重复目标时，rank 顺序与一次求值保持正确。
- 1,000 宽的两层队列在积累第二层时，不为树迭代器 heap 分配容量；单目标 heap 持有紧凑 ID，随后正确排空。

原有 18,800 个独立全重算模型批次、32 × 200 节点可达性模型、暂存表模型、同批次双源/自连接/不同深度 join、group/distinct/sort/top-k、预算耗尽回滚重试，以及失败 payload 释放和级联退休测试全部保留并通过。

标准 native Cargo：fmt --check、check/clippy --all-targets --all-features（Clippy -D warnings）、test、doc --no-deps（rustdoc -D warnings）、Rust 1.88 check/test、Rust 1.99 release test 均通过。调用级清空 rustc wrapper，显式使用安装的 cargo/rustc/rustdoc；没有启用或安装 Blaze，没有改全局配置。bench/release 的 strip=none 仅绕开本机 rust-objcopy 动态库问题。cargo tree --edges normal 仅有本 crate。

## 内存

memory benchmark 10 轮，每轮 10,000 源 payload 加 10,000 映射 payload（各 256 字节），含多个算子；数据库和外部 snapshot 释放后，每轮 live payload 均为 0。drop 后 RSS 范围 29,792–30,656 KiB。紧凑 heap 只存整数，不新增 payload/plan 所有权；原有失败准备与退休回归继续验证释放。

RSS 含分配器缓存，短期样本不证明长期绝无泄漏。应用保留的 snapshot/payload 和自行构造的引用环仍由应用管理。
