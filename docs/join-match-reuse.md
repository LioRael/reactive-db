# Join 输入索引查找：复用稳定匹配的优化

2026-10-26。基线：31371a8。结论：保留收窄到 left join 的版本；不保留通用 inner/left 优化，也没有恢复此前被拒绝的批次索引候选。

## 保留的改动

只在以下条件同时满足时复用已提交结果：left join、左侧只有一行变更、该行原来存在且更新后仍存在、join key 不变、右侧没有输出变更。

旧结果已经证明左右行匹配；上述条件保证这个事实仍成立。因此 src/join/runtime.rs::JoinNode::prepare 从左侧 patch 直接取得新值，从已有结果取得右值，避免对每个结果再次调用左右 Overlay::get。相同的新旧匹配桶只枚举一次，避免重复候选及其去重开销。没有旧结果的候选仍走完整 overlay 路径，正确处理占位项。

src/join/output.rs 仅增加私有 Mode::right 借用访问器。M::OUTER 是编译期条件，inner join 不启用此优化。双边更新、join key 变化、插入/删除、多行左侧批次继续走原有逻辑。没有新持久缓存、额外输入索引、运行时参数、依赖或公共 API；仍是纯 Rust，无 unsafe/FFI/JS。

引用只在 prepare 内存活，不修改已提交状态。索引和结果仍在原 commit 阶段原子发布。省略的重复桶枚举仍收取原来的逻辑工作单位，保持执行预算与失败回滚边界；没有通过放宽预算取得性能收益。

大 fanout 仍需更新输出索引，不能把整个 join 宣称为 O(n)。本轮消除的是重复输入树查找和重复候选枚举，输出 BTreeMap 查询/更新仍然存在。

## 严格同实例对照

每个诊断构建使用同一个二进制、同一个 DB 与查询图，在窗口之间切换原路径和复用路径。3 个进程 × 每场景 4 个实例 × 2 轮；交替 fresh/churn 分配历史、旋转条件顺序，交替 ABBA/BAAB。每实例交替预热两模式共 512 次写入，越过默认 journal 的 128 批次容量（大 fanout 另受 change 数上限约束）。两个模式分别校准后使用同一偶数迭代数，目标约 25ms/窗口，使窗口末值相同。

每个四窗口块内 A/B 各取两个窗口均值，再取实例两轮中位数、进程四实例中位数。下表每格三个数对应三个进程，不是置信区间。最终收窄版共 2016 窗口、504 块。

| 场景 | baseline/baseline | reuse/reuse | baseline/reuse |
|---|---|---|---|
| unaffected | +0.34% / +0.49% / -0.51% | -0.31% / -0.10% / +0.26% | -0.09% / +0.05% / -0.81% |
| pruned | -0.38% / -0.58% / -0.06% | +1.59% / -0.98% / -0.10% | -0.18% / -0.54% / +0.52% |
| fanout1 | +0.77% / -0.86% / +0.10% | +1.12% / +0.35% / +0.44% | -1.34% / -2.08% / -2.53% |
| fanout1024 | -0.60% / -0.46% / -0.54% | +1.42% / +0.75% / +1.68% | -23.10% / -25.40% / -22.92% |
| inner10000 | -0.84% / +0.90% / -0.29% | +1.05% / -1.19% / -0.05% | +1.01% / +0.18% / -0.16% |
| layered | -3.94% / -2.81% / -1.40% | -4.54% / +1.67% / -0.64% | +0.27% / +1.96% / -0.03% |
| converging | +1.07% / +1.91% / +1.85% | -2.38% / -0.13% / -2.78% | -2.87% / -1.80% / +1.31% |

大 fanout 同实例稳定快 22.9–25.4%。fanout1 略有收益，但量级小于大 fanout；不把所有小幅变化概括成稳定加速。unaffected、pruned、layered 没有 join 节点，切换模式不改变计时区间内的算法，它们的波动也提供了噪声参照。收窄版的 inner/converging 不启用新逻辑。

这种诊断开关会改变代码生成，所以不能仅凭同实例结果接受产品改动。独立构建、独立进程对照与最终指令段核对同时保留。

## 独立进程空对照与 ABBA

针对方向不一致的短路径与汇合，额外执行 3 轮：baseline/baseline 空对照与 baseline/outer 配对交替，窗口 ABBA/BAAB，分别重新启动进程。每窗口 Criterion 30 samples、0.5s warmup、1s measurement。块内两份 A、两份 B 的 mean estimate 分别求均值，再计算比例；这些用于判断进程/实例波动，不能替代所有场景的更长测量。

| 场景 | baseline/baseline 三轮 | baseline/outer 三轮 |
|---|---|---|
| scheduler/converging/10000 | +0.90% / -0.29% / +0.42% | -0.98% / +2.11% / +0.13% |
| scheduler/pruned/10000 | +5.86% / -6.90% / -8.64% | -7.10% / +1.32% / -5.55% |

短路径在相同基线二进制之间也可波动约 6–9%，配对结果没有稳定退化方向。汇合配对为 -0.98%、+2.11%、+0.13%，没有复现通用版本的持续偏慢。仍不能保证任意分配器状态或其他 CPU 都绝无小幅退化；本轮接受依据是结构性减少查找、显著且重复的大 fanout 收益，以及保护场景未出现可重复的退化。

## 硬件计数器与热点证据

本机 Apple M2 Pro，使用已安装 Xcode 的 CPU Counters。先对“仅复用匹配、不省重复枚举”的中间版做三轮两组事件，共 12 份记录：l1d_metrics 与 discarded_sampling，顺序 AB/BA/AB。这一步单独验证减少输入查找的效果，避免把枚举优化混为同一原因。最终收窄版再做一组 baseline/outer 的条件分支复核，共 14 份记录。

每份录制 6s，目标为 join_shapes/fanout/1024、--profile-time 12。分析主线程 2.0–5.5s 内完整且不超过 20ms 的片段，按 S/E 核分组，下表仅 S 性能核。中间版有效覆盖约 3.298–3.471s，周期/时间约 3.146–3.197GHz；最终复核覆盖 3.454/3.463s，约 3.164/3.174GHz。未锁核/锁频，各组分别采集；计时期间未并行运行本任务的编译、测试或其他 benchmark。

| 指标：基线 → 中间版 | 第 1 轮 | 第 2 轮 | 第 3 轮 |
|---|---:|---:|---:|
| 条件分支误预测 / 百万周期 | 13227.9 → 11928.1 | 13224.3 → 12011.3 | 13003.0 → 11682.7 |
| L1D load miss / 千次 load uop | 37.733 → 37.728 | 36.702 → 37.155 | 36.627 → 40.225 |

条件分支误预测/周期下降约 9–10%，L1D miss 比例没有改善。结合源代码与同实例收益，支持“消除重复查找及其分支”的解释，而非缓存命中率提高。没有声称证明具体分支预测器别名机制，也没有把误预测/周期当成误预测概率或每操作计数。

最终收窄版复核的条件误预测/百万周期为 12871.1 → 12589.0（约 -2.2%）。这是单组复核，不能称作三轮最终版计数器稳定收益；最终版还省略了重复枚举，周期分母与剩余工作构成均改变，不能直接用此百分比解释约 21% 的耗时下降。

PMI 进一步定位：中间版第一组，基线 join prepare 辅助闭包样本 3383，复用版为 0；最终组为 3049 → 1。统计覆盖所有 join prepare 辅助闭包名称，避免因编译器改变闭包编号而误报消失。基线主热点对应此前确认的输入 BTreeMap 查找闭包。最终主要热点变为输出树 insert/get（7510/6000 个样本）；这些是采样数量，不是精确误预测次数。每 0.5s 的热点分布确认 2–5.5s 内持续在处理 join 写入，而不是只测到初始化。

事件定义来自本机 RecountDT 的分析配置：discarded_cond_branch 对应 BRANCH_COND_MISPRED_NONSPEC。使用 Instruments 已归属线程的 MetricTable，未跨核相减原始累积 PMC。全部 14 次录制返回 54；日志显示时间限制结束、文件保存，导出成功且非空，TOC 与原始日志保留。未把它们标记成退出 0，也未推断未文档化退出码含义。

## 为什么不保留通用版本

只复用值的第一候选：同实例 fanout1024 三进程快 17.68%、18.00%、18.24%，但独立二进制筛选的 fanout/汇合方向不一致。

再省略重复枚举的通用 inner/left 候选：同实例 fanout 快约 23–24%、inner10000 快约 5%，然而独立构建较长测试的汇合三轮分别慢 4.61%、0.56%、16.40%。同实例汇合未稳定复现这些回退，说明不能仅归因于新增判断；布局和实例影响仍在。没有把这个通用版本合入。

最终用编译期 M::OUTER 限定适用范围，保留大 fanout 的收益，将 inner join 从本次优化范围中移除，再重新完成独立构建、同实例、ABBA 与硬件复核。没有通过随机代码 padding、全局编译选项或更换分配器选择一个偶然有利的结果。

## 回归与最终验证

新增 tests/join_match_reuse.rs 的两项回归：

- 独立全重算模型逐步检查 inner/left 输出：连续 payload 更新、已有未匹配占位、key 移动、同批次右侧更新/删除、后续单左侧更新；检查 delta epoch、旧/新值与右值 Arc 身份，失败与最终释放后的 Weak。
- 精确工作预算边界：64 个匹配时，基线及三个候选均为 input=1、output=65、work=198；197 必须失败并保持 epoch、快照和订阅不变，198 成功且统计一致。

已有双边原子发布、自连接、全重算、稀疏调度、预算回滚与节点释放测试均一并运行。

最终原生 Rust 1.99：check --all-targets --all-features、clippy --all-targets --all-features -- -D warnings、debug/release test、doc（警告视为错误）通过；debug/release 各 111 测试（含 doctest）。MSRV 1.88 check 与 111 测试通过。10 轮内存 benchmark live_after_drop 全部为 0，RSS 保留约 28–29MiB；没有将分配器保留页误报为未释放对象。三个诊断 harness 的 build/clippy 通过。

使用绝对路径原生 Cargo/RUSTC/RUSTDOC，并清空调用内 RUSTC_WRAPPER/RUSTC_WORKSPACE_WRAPPER。已安装 cargo blaze 的帮助显示 ra-jit 行为，兼容性不确定，因此未用于验证，未修改全局配置。

产品重新构建后，core 与 scheduler benchmark 的 Mach-O __TEXT,__text 字节数及 SHA-256 与已测 outer 候选一致（product-text.json）。这验证了最终代码的指令段没有因移回项目而再次改变；不是声称整个二进制所有元数据都相同。

## 复现与材料

benchmarks/join_match_reuse.rs 是实际测量的最终同实例 harness；benchmarks/join_match_reuse_probe.patch 是仅供诊断的切换补丁。补丁以 31371a8 为基线，不能直接应用到已包含优化的 HEAD。

在临时目录导出 git archive 31371a8，用 patch -p1 应用该补丁，把 harness 复制为 examples/strict.rs，再用原生 Rust 1.99 构建 --release --example strict。分别以 BENCH_RUN=0、1、2 顺序运行，保存 CSV；不要在产品分支启用诊断开关。分析器先按 CSV role 列组成 ABBA/BAAB 块，再按实例、进程聚合。

证据包包含原始 CSV、Criterion estimates、计数器 MetricTable/TOC/PMI XML、采样配置、原始日志、分析与执行脚本、所有候选补丁、验证日志和 SHA-256 清单。历史驱动脚本保留当时的本机路径；复现需要先固定上述基线并建立对应临时副本，不应直接对当前 HEAD 重跑历史 setup 脚本。完整 .trace 目录仍在本任务 work/join-reuse，压缩包保存导出数据；在 Instruments UI 中重新打开需要对应 .trace。

没有改动 livequery 或 tanstack-db-rs；没有引入 JS 兼容代码、FFI 或依赖，没有部署或推送。数值适用于这台机器和这些工作负载，不作为其他平台的性能保证。
