# reactive-db：短路径的多实例、交叉顺序与跨进程验证

直接基线 `349ca50`。只修改 reactive-db 和任务验证目录；未改 livequery、tanstack-db-rs。纯安全 Rust、零运行时依赖，公共 API 不变。

## 结论与限制

短路径收益比上一轮更可重复：正常版本角色的实例配对中位数，无关节点写入 **降低 10.5%**、剪枝 **降低 10.3%**；交换版本角色后分别降低 **13.7% / 10.3%**。两种创建顺序、两种计时顺序和六个比较进程均保持改善方向。正常角色下聚合耗时约从 **234→208 ns、265→237 ns**，约省 26–28 ns；这是本机测量结果，不能保证固定纳秒数跨机器成立。

独立编译的两个版本也验证了方向：无关节点两组成对变化为 **-12.4% / -20.9%**，剪枝为 **-15.1% / -5.3%**。因此本次保留单行源发布快路径，而不是根据单一实例的最快窗口决定。

空对照确实揭示偏差：前置同源剪枝在三个进程中为 +12.7%、+2.2%、-3.5%；正式 old_null 的剪枝按创建顺序分组为 -8.5% / +6.8%。这些差异足以污染几十纳秒级比较。独立实例重建、创建顺序交叉、角色互换和跨进程重复不能消灭所有噪声，但能避免把某一实例位置当成版本收益。

**保留收益场景的实现没有改动，但不能宣称所有测量零回退。** 大 fanout 在正常同进程角色下约慢 5.5%，角色互换后只慢 0.4%，独立版本对照为 +1.5% / -1.1%；数据提示明显布局/进程依赖，没有跨方法一致的大 fanout 退化。多层宽图同进程仍有 **+1.6% / +3.3%** 的小幅回退信号，独立对照为 +11.5% / -5.5%，不能完全排除小幅真实回退。join 汇合正常/反向角色分别 -1.2% / +0.5%，独立测量方向也不一致。下表完整保留这些结果，没有用历史不同实验的绝对时间证明“全面超过原版”。

## 实现与可验证的成本

`State::changes` 现在在源 patch 只有一个条目时，消费其拥有的 ID，完成同样的工作和输出预算检查，然后直接从 `[Change; 1]` 构造 `Arc<[Change]>`。它去掉了一次临时 Vec 分配及中间转移步骤，以及一次源 ID 克隆。没有改变写入的 sparse overlay、源索引、派生算子、调度器或发布边界。

空 patch 和多条目 patch 继续走原来的 Vec 路径。单条目最终没有变化时返回空共享切片；相同 Arc 无变化，但内容相等的新 Arc 仍产生替换事件。预算检查仍先于输出发布。源集合查找的复杂度、准备顺序、delta 顺序和所有逻辑工作计数保持不变。这不是整次写入零分配，也不是重写节点表来换取平均查找速度。

大 fanout 的借用候选和稳定去重、单一候选内联、多层宽图的紧凑队列、单行 join 索引补丁均未改动。

## 新测量设计

环境为 Apple M2 Pro、16 GiB、macOS 27.0.1、Rust 1.99.0 release。前置与最终测量都串行运行；没有与本任务的构建/测试并行计时。没有锁 CPU 频率或控制系统其他后台负载，因此结论仍限于此机器、这些工作负载。

先建立源码完全相同的两个 crate 副本，跑 3 个独立进程。每进程每短路径重建 4 对实例，每对 4 个相邻计时窗口对；目标约 50 ms/窗口。它测量同源代码在不同实例、模块/布局与进程环境下的偏差，不能把其方向固定地从最终结果中相减。

最终同一可执行文件链接基线与候选，运行 **3 个新进程**。每进程、每场景、每 suite 都重新创建 **8 对数据库**；每对实例完成校准和预热后，计时 **4 对窗口**，目标约 100 ms/窗口。每对使用相同写入次数，时钟只在循环外读取。四种组合均覆盖：A/B 谁先创建、A/B 谁先计时；校准先后也独立交叉。每进程轮换场景和 suite 顺序，两个实例在该实例试验结束后销毁，下一对从空数据库重新构造。

短路径有三个 suite：old_null（基线对基线）、new_null（候选对候选）、paired（基线对候选）。其余五个保留收益场景使用 paired。正式数据共 **1,056 个窗口对**；每个 suite/场景是 **24 对重建实例，分布于 3 个进程**。前置同源对照另外有 96 个窗口对。

先对每个实例的 4 个 after/before 比值取中位数，再汇总实例；表中的进程、创建顺序、计时顺序分组均保留。**重复窗口不是独立实例**，24 对实例也不等于 24 个独立进程；这里只有 3 个进程簇，不提供夸大的统计置信度。耗时栏是实例窗口平均 ns/op 经两级中位数聚合后的值；变化率按配对计算，不用两个独立汇总耗时直接相除。

两份基线 src 逐文件与 `349ca50` 对照，26 文件完全一致。用于最终旧版的副本不修改源码，仅独立 crate 名称和最小 manifest 便于同进程链接。宏生成等价负载；两个数据库/图同时驻留、相同动态闭包调用成本、独立哈希种子和分配地址仍可能影响短路径，空对照用于揭示而非掩盖这些差异。


追加两个交叉核对：

1. 交换依赖别名，使候选占用原 before 模块、基线占用原 after 模块；五个场景再跑 3 个新进程、每场景 8 对实例、每对 4 对窗口，共 480 对。汇总时翻转时间值及创建/计时标签，表中 before 始终指基线。原始反向 CSV 保留原角色标签，使用时应先归一化。
2. 基线/候选各自独立编译，用现有 Criterion harness 跑 5 个重点场景，40 样本、1 秒预热、3 秒 measurement，两组成对 A→B / B→A，并逆转场景顺序。两侧预先构建，不把编译计入时间。表中的范围是两次运行中位数范围，不是置信区间；每次 median/mean 的 CI 另存 JSON/CSV。

同进程数据共 1,536 对正式窗口（正常 1,056、反向 480），加前置对照 96 对；独立 Criterion 共 20 组 estimates。正常与反向角色是不同链接布局，不直接相减绝对耗时。

## 回归与资源语义

新增 3 项测试，共 **103 项**（90 unit/integration，13 rustdoc，含 10 compile-fail）：

- 独立行模型检查单条目和添加一个 no-op 后的多条目路径：插入、删除、替换、相等内容的新 Arc、缺失行抵消、相同 Arc；检查 before/after、工作和输出计数，以及准备前后状态。
- max_work=0 或 max_output_changes=0 拒绝单行源发布后，Weak 确认暂存 payload 已释放，源状态保持为空。
- 单行源发布消费已拥有的 ID，不调用 Clone。该测试用于锁定消除多余克隆这一成本。

原有全重算模型、跨集合原子发布、自连接、join key 变化、delta 订阅、预算精确边界、退休与释放测试全部保留。源的共享 delta 类型不变，仍在所有算子准备成功后统一提交；错误路径和 panic poison 契约不变。

标准 Cargo check/clippy（all-targets/all-features，-D warnings）、test、release test、fmt check、rustdoc（-D warnings）通过；Rust 1.88 的 check/test 通过。比较 harness 独立编译并通过 clippy。调用工具链绝对路径并清空两个 RUSTC wrapper，未经过 Blaze、未改变全局配置。

将新增语义/释放回归放回基线也通过；ID 克隆回归在基线按预期失败（1 次 Clone），候选通过（0 次）。测试不是简单断言某个实现分支存在。

内存 benchmark 连续 10 轮、每轮 10,000 行、每 payload 256 字节；database 与外部 snapshot 释放后每轮存活 payload 都为 0。RSS 约 30.1–31.4 MiB 后趋于平稳；分配器可保留页，RSS 不作为“所有场景无泄漏”的证明。

## 复现

`benchmarks/rebuilt.rs` 是独立比较 harness，不加入库的运行依赖或默认 Cargo targets。创建比较工程并复制为 `src/main.rs`，配置两个路径依赖：`old_db` 指向基线导出的源码副本（package 名 `reactive-db-baseline`），`new_db` 指向当前 reactive-db。基线副本使用 Rust 2024、MSRV 1.88、无运行依赖；仅改独立副本的 package 名以同时链接。

```toml
[package]
name = "rebuilt-benchmark"
version = "0.1.0"
edition = "2024"
[dependencies]
old_db = { package = "reactive-db-baseline", path = "before" }
new_db = { package = "reactive-db", path = "/Users/leosouthey/Projects/reactive-db" }
```

先 `cargo build --release --offline`，再分别以 `BENCH_RUN=0`、`1`、`2` 启动可执行文件，分别保存 CSV；不要同时运行这些进程。`BENCH_RUN` 只控制场景、创建、校准、计时顺序，不改变数据库数据。`BENCH_CONTROL=1` 选择前置对照的两个短路径及 4 对实例；重现前置同源控制还需将两边都指向基线源码，当时目标窗口为 50 ms，正式 harness 为 100 ms。

角色互换时交换两个依赖的 package/path，保持基线源码不变；本轮反向测量只保留 unaffected、pruned、fanout1024、layered、converging 的 paired suite。原始反向 harness 与 CSV 一并保存在交付附件，归一化规则如上。

独立版本示例：

```sh
cargo bench --bench scheduler --locked --offline -- 'scheduler/unaffected/10000$' --noplot --sample-size 40 --warm-up-time 1 --measurement-time 3 --save-baseline before
cargo bench --bench core --locked --offline -- 'join_shapes/fanout/1024$' --noplot --sample-size 40 --warm-up-time 1 --measurement-time 3 --save-baseline before
```

实际调用显式 Rust 1.99.0 工具链路径，清空两个 wrapper；为绕过本机 rust-objcopy/LLVM 兼容问题，基线与候选一致使用调用级 `CARGO_PROFILE_BENCH_STRIP=none`、`CARGO_PROFILE_RELEASE_STRIP=none`。没有修改全局或项目 Cargo 配置。生产源码改动仅 15 行单行源准备逻辑；其余为回归、benchmark 与文档。
