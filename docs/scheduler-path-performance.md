# reactive-db 调度热路径优化与性能验证

日期：2026-10-26。直接基线 `c401f1b`；全图扫描参考 `dca6164`。只修改 reactive-db 和任务验证目录，未改动 livequery、tanstack-db-rs。保持安全纯 Rust、零运行时依赖、现有公共 API。

## 实现与语义

剩余成本不仅在 ready 队列，也在每个派生节点读写 delta 暂存表。此次没有修改算子算法或回退到全图扫描。

- **队列最小序列内联**：`src/scheduler.rs` 的 Queue 直接持有最小的依赖序列，其他序列才进入 BinaryHeap。只有一个序列时不为 ready 索引分配堆空间。序列推进时与堆顶交换，仍严格按 rank 归并；相同 rank 去重，新产生的边只能指向当前父节点之后。
- **首个暂存项内联**：新增 `src/stages.rs`。常见单源或剪枝场景只用内联项；同源宽扇出的所有子节点可直接读取这个源。其余节点 delta 和维护状态使用标准库 HashMap 查找，避免 BTreeMap 的逐项排序。只优化索引，不声称整个事务零分配：payload、Box、patch、commit Vec 等仍可能分配。
- **存储与顺序分离**：WriteBatch 的源 patches 继续使用 BTreeMap；Database 在准备源时建立提交列表，按该顺序播种，再按拓扑顺序追加派生节点。HashMap 不参与调度顺序或发布顺序。移除首项后重插已有哈希项不会形成重复键。
- **原子性与预算不变**：全部源先暂存，随后执行受影响节点；全部普通错误检查完成后才提交。仍在序列入队前按边数收费，到达节点求值前收费，成功批次的逻辑 work 定义不变。empty delta 阻止下游，但 join/group/order 的必要索引维护仍提交。
- **生命周期不变**：ready 队列和两个暂存表都属于本次写入，成功、预算失败或 unwind 后释放，无跨批次 visited 标记、scratch 高水位或持久 delta 缓存。租约退休事件、调度元数据容量收缩、订阅和外部 snapshot 所有权保持不变。应用代码 panic 仍 poison 数据库。

运行时节点仍使用 BTreeMap，因此全局节点查找仍有 log(V) 成本；这次未宣称所有成本都只与 delta 数量线性相关。暂存溢出表为期望 O(1) 查找，队列为有序序列归并。没有给公共键增加 Hash 约束，哈希键只是内部 NodeId。

## 回归验证

新增 4 项测试，总计 **88 项**通过（75 unit/integration，13 rustdoc，其中 10 compile-fail）：

1. 单序列不分配 heap，弹出后加入更早子序列、跨 inline/heap 交换和重复目标，仍按正确顺序只返回一次。
2. 内联暂存替换立即释放旧引用，退出后哈希暂存也释放引用。
3. 16 个种子 × 500 次插入/替换/删除，与独立 BTreeMap 模型比较所有键，覆盖首项删除后的重插和溢出表中的同键替换。
4. 1,000 个派生节点在准备到一部分时耗尽 output 预算：所有暂存 payload 立即释放，源未发布；重试后得到全部 1,000 个输出，退休后再次全部释放。

此前的 18,800 个独立全重算模型批次、32 × 200 节点可达性模型、双边 join、自连接、不同深度汇合、left join、group/distinct/sort/top-k、预算中断重试和级联退休回归保持通过。

验证通过：标准 native Cargo fmt --check、check/clippy --all-targets --all-features（Clippy -D warnings）、test、doc --no-deps（rustdoc -D warnings），Rust 1.88 check/test，Rust 1.99 release test。调用级清空 rustc wrapper 并显式指定安装的 cargo/rustc/rustdoc；Blaze 没有用于最终验证，也未改变全局配置。bench/release 的 strip=none 仅用于避开本机 rust-objcopy 动态库问题。cargo tree --edges normal 仍只有 reactive-db。

## Benchmark 方法

Apple M2 Pro，16 GiB，macOS 27.0.1，Rust 1.99。独立目录导出两个基线，逐文件验证 src 与相应提交一致；所有版本使用同一 benchmark、manifest 和锁文件。构建/测试没有与本任务的计时循环并行。

主测试：22 场景，按 original → before → after → after-repeat → before-repeat → original-repeat 顺序运行；30 样本、150 ms warmup、500 ms measurement、10,000 bootstrap resamples，共 132 次测量。新增 10,000 宽度的两层图和 join 汇合。Criterion 在慢场景中会延长实际采集时间以满足样本数。

万节点两层图短采样波动较大，因此增加专项：万节点 affected/layered/pruned 三场景，before → after → after-repeat → before-repeat，50 样本、1 s warmup、3 s measurement，共 12 次长采样。专项没有重新测量全图扫描原版；不可把专项与主测试绝对时间混合计算增益。

以下范围是两轮中位数的最小/最大值，**不是置信区间**。CSV/JSON 保留每轮 median、95% bootstrap CI 和 mean。百分比以两轮中位数的算术平均比较，作为描述性结果，不代替跨进程显著性检验。

复现主测试：`cargo bench --bench scheduler --locked`。

本次未重跑原 core benchmark 的全部算子场景，也没有声称得到采样 profiler 的函数级耗时占比。定位依据是调用路径、专门回归和相同 harness 的版本对比。

## 内存释放

memory benchmark 10 轮，每轮 10,000 源行加 10,000 映射行（256 字节 payload），物化多个算子，释放数据库和外部 snapshot 后每轮 live payload 均为 0。drop 后 RSS 为 31,808–32,896 KiB。新增失败准备回归验证了新暂存结构在错误路径也释放所有 payload；现有峰值元数据容量回收和退休事件回归继续通过。

RSS 含分配器缓存，短期测试不等同于长期无泄漏证明。应用持有的 snapshot/payload 和应用自行构造的引用环仍由应用管理。
