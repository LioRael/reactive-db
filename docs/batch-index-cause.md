# 批次索引与 fanout 回退：profiling、分配及布局对照

基线 `790e302a2c695f9321b771aea01823c16f5e43f1`，Rust 1.99.0 / aarch64 macOS。**本轮未保留新的运行时优化**；`src/`、依赖、工具链配置与基线相同。此前短路径、宽图、大 fanout、稀疏调度优化均保留。本轮交付诊断基准、可复现的实验补丁、1 项新回归和测量证据，未修改 livequery 或 tanstack-db-rs。

## 已定位到哪一层

原候选的退化在原 Criterion fanout/1024 基准中再次复现，三轮耗时变化为 **+9.78% / +3.40% / +4.90%**。这是真实测到的构建产物回退，不能仅因少分配一次就忽略。

但证据不支持“批次索引增加了 fanout 的算法工作量或额外分配”：

- 原生 malloc 全历史记录：同一进程内初始化完成后，对 **10 次写入**作前后差分，基线 10,584 次 ALLOC、候选 10,574 次；请求字节分别 3,449,440 和 3,446,640。两边差异**恰好是 10 次 280 字节分配**，其余尺寸直方图逐项相同。计数包含相同的诊断握手开销，不把总数除以 10 宣称为严格的产品分配次数。基线/候选 FREE 增量分别 323 / 313，也少 10 次释放。源注册表少分配一次的效果确实存在。
- 4 秒、1ms 的 `sample` 采样中，热点是 join 结果 BTreeMap 的 get、insert 和输入 overlay 查询；没有新增批次索引热点。采样只能定位主要工作，不能分辨几十纳秒源索引成本，更不能直接证明缓存 miss 的来源。
- 对**复现退化的 core 程序**做反汇编：结果树 get / insert 分别 83 / 103 条指令，去掉跳转目标绝对地址后逐条相同。join prepare 两版均 1,309 条，差异集中于常量地址和链接 stub；未出现新遍历或新调用链。prepare 起始位置 mod 64 为 36 / 48。这里只对比这些热点，不宣称整个程序机器码相同。
- 固定一个程序、同一张图，每轮切换旧树/内联注册表：短路径在三进程中持续改善约 10%–13%；fanout 不再呈现固定的 8% 回退。额外用原 Criterion 的“左右集合在同一批次初始化”方式验证，旧索引初始化组为 +1.03%、+0.71%、−0.10%，内联初始化组为 +0.17%、+0.37%、+0.42%。这削弱了“少一个分配本身或双集合初始化必然使 fanout 慢 8%”的解释。

**当前结论：回退具有明显的构建布局/实例状态敏感性，不是新增的 fanout 算法复杂度或更多堆分配；微观根因尚未完全隔离。** 固定程序实验本身带有诊断分支，会改变代码生成，所以不能据此断言原候选在所有应用中没有退化。尚未测硬件缓存/分支预测计数器，也未控制系统调度、CPU 频率或每个 HashMap 的随机状态，不能把所有差值精确归到指令缓存、数据缓存或 allocator 中的某一个。

## 实验设计与边界

- 所有构建、正式 benchmark、采样、分配记录、测试串行执行，正式计时不启用 malloc logging 或 profiler。
- 旧候选是前一轮归档的批次注册表内联实现；没有修改 join 或调度算法。
- 固定程序诊断用安全 Rust enum 在每次写入创建批次时选择旧树或内联实现；TLS 开关只存在于临时导出副本，不在正式运行时。每种初始化模式、每个场景重建 4 个实例，每个实例 4 个交替计时窗口，3 个独立进程。先对实例内比值取中位数，再对每进程 4 个实例取中位数。不是把窗口当作独立样本。
- 两个初始化模式都经过旧/新两种写入方式的预热；因此测的是预热后的交替稳态，不能据此排除只在首次写入出现的初始化影响。
- 构建/实例对照沿用现有调度基准：unaffected、pruned、10,000×2 层宽图、10,000 个汇合 join、fanout 1024。固定程序正常矩阵 480 行，补充同批次初始化矩阵 96 行。
- 原 Criterion 复现与对齐实验各 3 轮 AB/BA/AB，40 samples，1s warmup，3s measurement。两个替代实现是筛选实验，各 2 轮正反顺序，20 samples、0.5s warmup、1s measurement；它们用于拒绝候选，不用于宣布稳定优化。
- 原生工具链绝对路径调用，单次调用清空 RUSTC_WRAPPER / RUSTC_WORKSPACE_WRAPPER；Blaze 的行为/兼容性未充分确认，没有使用或修改持久配置。两边 bench/release strip 都关闭以避开本地 strip 工具问题。

## 分配记录的方法

使用 `MallocStackLoggingNoCompact=1` 单独启动诊断进程，初始化后阻塞读取 stdin；外部采集 `malloc_history PID -allEvents`，放行 10 次写入，第二次采集，再让进程退出。

必须只设置 NoCompact：本机 `man malloc_history` 明确两种变量同时设置时 MallocStackLogging 优先、NoCompact 被忽略。早期同时设置两者得到的是压缩记录，只用于识别存活对象，**没有拿它当完整分配次数**。归档中以 `full-events` 命名的文件才用于上述分配结论。分配日志记录的是请求尺寸；系统分配器实际 size class 可以不同。

## 函数对齐对照

只在临时构建中给两边同时增加 `-C llvm-args=-align-all-functions=6`，验证三个热点入口均为 64 字节对齐。源码和分配算法不变，观察布局敏感性。三轮 fanout 差值为 **-0.75% / +19.30% / -16.30%**。

结果不稳定且方向反转，**没有保留这个配置，也没有将其作为性能修复**。它证明原来的正向差值不能跨编译布局直接推广，但不足以断言准确根因就是入口对齐；全程序对齐还改变代码体积、函数相对位置，独立进程也有调度和实例偏差。未修改 Cargo.toml、全局 flags、CI 或工具链。

## 尝试过的替代实现

1. 在原内联注册表候选上给 `WriteBatch::record` 加 `inline(never)`，减少批次写入代码嵌入调用点的影响。
2. 改为 Empty / One / Many 的紧凑枚举，第二个集合才晋升为有序树。实测本机 WriteBatch 体积：基线 112 字节、原候选 136 字节、紧凑候选 120 字节。晋升后仍按 source ID 顺序消费。

| 场景 | record 不内联：AB / BA | 紧凑枚举：AB / BA |
|---|---:|---:|
| join_shapes/fanout/1024 | +8.3% / +7.8% | +3.2% / +1.9% |
| scheduler/unaffected/10000 | -18.7% / -11.0% | -17.7% / -15.8% |
| scheduler/pruned/10000 | +4.3% / -4.8% | -3.2% / -0.2% |
| scheduler/layered/10000 | -0.2% / -3.4% | -1.2% / -13.0% |
| scheduler/converging/10000 | +2.4% / +2.1% | +3.4% / +5.2% |

隔离函数没有解决 fanout；紧凑表示减轻了 fanout 回退，却在两个汇合对照中均退化。两者都通过 source_order 回归，但性能保护未通过，**均不进入正式运行时**。不继续用随机 inline 调整去追逐某个构建产物的有利布局。

## 回归与交付验证

新增 `tests/fanout_batch.rs`：1,024 路 left join 在匹配/未匹配之间反复迁移 key，以独立全重算模型验证全部结果 ID；每次先将输出预算限制到中途失败，验证源/视图 epoch 和订阅不发布、失败准备中的载荷释放，再放宽预算原子重试，验证 1,025 条转换同一 epoch 发布。最后释放 owner、句柄与订阅，Weak 证明历史载荷也被释放。

- 基线、原候选、隔离函数候选、紧凑候选都通过该回归；后两者另通过既有 source_order 回归。
- 最终产品：标准原生 Cargo check(all-targets/all-features)、clippy(-D warnings)、fmt、doc(-D warnings) 通过；1.99.0 debug/release 与 MSRV 1.88.0 完整测试分别 **108 项通过**。
- 10 轮内存 probe 的 `live_after_drop` 全为 0。RSS 仅作诊断，不以页未归还操作系统判断泄漏。
- 诊断副本另行通过 clippy。归档保留正式计时使用的原始源码；仓库诊断补丁仅另作格式、文档和等价 let-chain 清理。
- 正式 `src/`、Cargo.toml、Cargo.lock 与基线无差异；没有 unsafe、JS 兼容、FFI、新依赖或运行时诊断开关。

## 复现入口

`benchmarks/batch_index_probe.patch` **只应用到临时基线快照**，不要应用到产品 checkout。把 `benchmarks/batch_index_probe.rs` 复制为该快照的 `examples/batch_index_probe.rs`，以原项目工具链构建；`BENCH_RUN=0/1/2` 分别直接运行 release example 并保存 CSV。这份精简入口复现同批次双集合初始化、同实例交叉计时。完整五场景测量入口和原始未清理诊断源码保存在附件证据包。

原 Criterion 入口仍为 `cargo bench --bench core -- 'join_shapes/fanout/1024$' --noplot --sample-size 40 --warm-up-time 1 --measurement-time 3`。进行版本对照时各自使用独立导出快照，按 AB/BA/AB 顺序串行运行；不要在产品工作目录直接覆盖候选。证据包包含原候选和两个替代候选的源码差异、原生 sample、分配历史、反汇编、CSV、Criterion JSON、验证日志和工具脚本。
