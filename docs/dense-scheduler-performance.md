# reactive-db 密集调度优化与三版本性能比较

日期：2026-10-26。直接基线 `2af6397`，全图扫描参考 `dca6164`。
工作范围只有 reactive-db 和独立验证目录；未改动 livequery、tanstack-db-rs。纯安全 Rust，零运行时依赖，公共 API 不变。

## 实现

本轮针对两项成本：依赖边的重复排序/分配，以及每个派生节点传播时的调度元数据查找。

1. **有序依赖序列合并**（`src/scheduler.rs:10`）：每个父节点的后继已经按拓扑 rank 排好。ready 队列改为小顶堆，堆元素持有一个后继集合的借用迭代器；宽扇出不再逐边构造 BTreeSet ready 条目。弹出最小 rank 时推进对应序列，汇合产生的相同 rank 一并去重。所有新加入的边严格指向当前父节点之后，因此同一节点只求值一次，且其受影响祖先均已处理。
2. **整段边预算**（`src/budget.rs:79`）：序列加入前用已知长度收费，不再为收费扫描每条边；检查剩余额度后才相加，不发生整数溢出。成功批次的逻辑 work 定义不变：每条传播边一次、每个到达节点一次，汇合的不同边仍分别计数。失败时不加入半条序列，也不发布已暂存的源、视图、索引或 epoch。
3. **直接元数据查找**（`src/scheduler.rs`）：只按私有 NodeId 查找的元数据表改用标准库 HashMap，不迭代它决定执行顺序。拓扑 rank 与有序子节点集合仍控制求值次序。没有增加依赖或自定义哈希算法。
4. **退休后的容量回收**（`src/scheduler.rs:118`）：事件回收完成后，仅当容量超过存活项四倍且超过小容量门槛 16 时收缩。避免逐节点缩容，也不无限保留峰值 HashMap 容量；可能留下有界的余量。稀疏写入没有恢复全图扫描，只有大量退休后的缩容会重排剩余元数据，其成本可由本次大量移除摊销。退休清理仍不计入逻辑执行预算。

持久反向边依旧为 O(V+E)。队列空间随同时活跃的非空依赖序列 R 增长；宽单源扇出的队列只需一个序列。合并成本约 O(E_visited log(R+1))，另有去重、算子计算和节点/暂存 BTreeMap 查找。HashMap 元数据查找是期望 O(1)，不是最坏情况保证。没有引入按历史最大 rank 分配的数组、跨批次 visited 标记或常驻 scratch 缓冲；失败/退出后局部队列释放，也没有 marker 重置或失败重试污染。

原子发布仍由原有 prepare→commit 流程保证；空 delta 截断传播，但必要的 join/group/ordered 索引维护仍提交。租约退休、订阅保留、外部 snapshot 所有权和 panic 后 poison 语义保持不变。

## 验证

本轮新增 6 项测试，累计 84 项通过：71 unit/integration 和 13 rustdoc（包括 10 compile-fail）。

- 10,000 边扇出仅保留序列级队列状态，共享序列去重后输出一次。
- 32 个确定性种子、每个 200 节点的动态汇合/剪枝 DAG，与独立拓扑可达性模型一致。
- 序列预算 99/100 的边界拒绝/接纳，销毁队列、移除节点后重新调度正确。
- 队列执行到一部分时预算失败，所有源、视图、订阅和 epoch 保持旧状态；重试完整，退休后不再调用原投影。
- 128 个共享父节点 join，10 个批次重键，双方不同深度，每节点只发布最终值一次。
- 10,000 派生节点退休后反向边为空，元数据峰值容量回收；重新注册使用新 rank。

此前 18,800 个批次的独立全重算模型、稀疏 work 计数、同批次双边 join、自连接、left join、empty-output 维护、group/distinct/top-k、订阅与级联释放回归全部保留并通过。

标准 Cargo 验证通过：fmt --check、check --all-targets --all-features、clippy --all-targets --all-features -- -D warnings、test、doc --no-deps（rustdoc -D warnings），以及 Rust 1.88 的 check/test、Rust 1.99 release test。显式使用安装的 native cargo/rustc/rustdoc，并清空本次调用的两个 rustc wrapper 环境变量；未安装/启用 Blaze，也未改全局配置。release/bench 的 strip=none 仅为绕过本机 rust-objcopy 动态库问题。cargo tree --edges normal 仍仅有 reactive-db。

## Benchmark

Apple M2 Pro / 16 GiB / macOS 27.0.1，Rust 1.99。两个基线从提交导出到独立目录，逐文件核对 src 与对应提交一致，使用同一 benchmark 源码、manifest 和 lockfile。

顺序为 original → before → after → after-repeat → before-repeat → original-repeat；计时期间没有同时运行本任务的构建或测试。Criterion 每场景 30 样本、150 ms warmup、500 ms measurement、10,000 bootstrap resamples。20 个场景 × 6 轮，共 120 次测量。新增两层宽图和 join 汇合，避免只用单层扇出评价堆合并。

结论：本次减少了上次引入的密集调度开销，并保留仅传播受影响节点的收益；不宣称所有规模均胜过全图扫描或每个短场景都变快。小规模密集图仍有维护反向依赖和队列的固定成本，亚微秒稀疏操作也有测量波动。详见三版本范围与相对差值，不将某一轮最佳值外推为通用加速比。

万节点 filter 剪枝场景，本轮约 0.426–0.432 µs，上次约 0.380–0.389 µs，增加约 45 ns（约 12%）；仍远低于全图扫描原版的约 393–399 µs。这是目前保留的固定开销权衡，不能将“保留稀疏收益”描述成每个稀疏微基准都无退化。

复现命令：`cargo bench --bench scheduler --locked`。原 core benchmark 保留，本次未重新测量其全部算子场景。

## 内存

10 轮 memory benchmark，每轮 10,000 源 payload 和 10,000 映射 payload，各 256 字节，包含 join/group/distinct/top-k；释放数据库及外部 snapshot 后每轮 live payload 均为 0。drop 后 RSS 范围 31,008–31,920 KiB。另有峰值元数据容量回收单测和执行中断后的队列/租约回收回归。

RSS 含分配器缓存，短期观测不等同于长期无泄漏证明。调用者保留的 snapshot/payload 和用户自建引用环仍由调用者管理。
